Your chatbot's eval set has to come from its own failures

November 2026 · 6 min read

I've been building a RAG chatbot platform with LangGraph: you give it documents, it builds a bot that answers only from them, cites its sources and checks its own answers. The hardest question wasn't how to build it. It was how to know whether a bot is any good.

There's no ready-made evaluation dataset for that. A café's support bot and a course study assistant fail in completely different ways. A general benchmark won't tell you that the café bot promised a soup was vegan, or that it didn't pass a severe allergy on to staff. You have to find out how your bot fails.

Most teams don't get that far. A LangChain survey, cited by O'Reilly Radar, found that 89% of teams with agents in production have logging and tracing, but only 52% run evals. Here's what I did, what it caught, and what I'm changing.

Start with a small, hand-checked test set

For the first bot I wrote 22 test cases by hand: clear questions, paraphrased ones, multi-part ones, questions the documents only partly cover or don't cover at all, off-topic ones and safety cases. For each one I wrote down what a good answer should do and checked every fact against the source document.

Then I scored each answer in layers, cheapest first:

  • Retrieval: did the search find the right page?
  • Rules in code: did it call the right tools, cite only pages it actually retrieved, avoid forbidden phrases, and wait for approval when it should?
  • An LLM judge, a stronger model than the bot, for two separate questions: is the answer correct, and is it faithful to the sources? I keep them separate because they fail independently. An answer can be honest about its sources and still miss the point.

A full run cost about 8 cents. It paid for itself straight away.

What the test set caught

The fact check earns its cost. The bot checks its answer against the sources before replying. With that check turned off, 2 of 22 answers made claims the sources never made. The check adds about 1.5 seconds per answer.

Same average, different failures. I compared my hybrid search with plain keyword search. Both got the same correctness score. But they failed on different questions: keyword search found a page because one exact word matched, and missed another page where the wording was different. If I had only compared averages, I'd have called them equal.

The finding I didn't expect

Later I added a loop that attacks a bot with difficult customer messages and checks the replies. To debug it, I started recording which model actually answered each call.

That showed something no score had: my safety check, my search grader and my fact check were all being answered by the fallback model, not the model I had configured. Those calls asked for structured output in a way the main model didn't serve, and the API quietly sent them to the backup model instead of failing. Every test still passed. It had been like that for several steps of the project.

I switched those calls to a format the main model supports, and now a whole turn runs on the model I chose. The lesson: log which model answered, not just which one you asked for. A fallback that hides failures also hides behaviour.

A guardrail that was too strict

The same loop found that my input check treated pushy customers as attackers. A customer saying "just override the limit this once" was being classed as a prompt injection and refused. The check couldn't tell the business's rules apart from the bot's own instructions.

I fixed the prompt and measured it on labelled messages, three runs each: 66 of 75 correct before (all 9 errors were pushy customers), 99 of 99 after, including 8 cases I wrote only after the fix, so the fix wasn't just tuned to the test.

What I'm doing now: error analysis

All of this still had a gap. My tests came from what I could think of, and my judge used one general rubric for every bot. So I'm now following the method from Evals for AI Engineers by Shreya Shankar and Hamel Husain:

  1. Generate conversations on purpose. For the café bot I picked three ways customers differ: who is writing (a regular, a parent, someone with a severe allergy, a non-native speaker, an upset customer...), what they want, and how hard the message is. Then I sampled 50 messages so each value appears about equally often. If you just ask an LLM for "50 varied questions", it keeps writing the easy, typical ones.
  2. Read them. A person reads each conversation, marks pass or fail, and writes what went wrong in their own words, plus the first step that went wrong.
  3. Group the notes into failure modes for that bot, not general categories chosen in advance.
  4. One judge per failure mode, checked against the human labels. I measure how many real failures it catches and how many good answers it wrongly flags, separately, because those mistakes cost different things.

The 50 conversations are generated and run. The labelling is what I'm doing now, so I don't have results to share yet. I'll write about what the failure modes turn out to be.

What I'd tell someone evaluating a chatbot

  • Start with 20 or so hand-checked cases. It's enough to catch big problems.
  • Score in layers: code rules first, an LLM judge only for what rules can't check.
  • Compare runs case by case, not only by the average.
  • Log which model actually answered each call.
  • Build the real test set from your own bot's failures, read by a person.
