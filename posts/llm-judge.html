My LLM judge failed answers that were right

November 2026 · 6 min read

I built an agent that triages GitHub issues. It suggests labels, finds duplicates and drafts a reply, and a person has to approve every action before it runs. At the end of each run the agent writes a short summary of what it did.

That summary can lie. It can say "I marked this as a duplicate" when the person rejected that action. So I added an LLM judge to check one narrow thing: is the summary faithful to what actually happened?

This post is about what went wrong when I started trusting that judge, and what I do differently now.

The judge said 93%. The real number was 100%.

In one of my eval runs, the judge marked 2 of 28 summaries as unfaithful. I opened both. Both were correct.

One summary said:

The duplicate marking was rejected.

That is exactly what happened: the agent proposed it and the person said no. The judge read "rejected" as "never called" and failed it. The other summary correctly said that the duplicate check had found the two issues to be different, and the judge failed that too.

So the score said 93%, and the truth was 100%. If I hadn't opened the failures by hand, I would have "fixed" an agent that wasn't broken.

So I tested the judge before trusting it

I built a small bank of 34 test cases, each one an agent run plus a summary, covering every way a summary can go wrong (claiming an action that didn't run, hiding a rejection, wrong issue number) and some borderline ones. I labelled 16 of them by hand. The other 18 were labelled by Claude using the same rules, and every case records who labelled it.

Then I measured how often each judge agreed with the labels, using Cohen's kappa (1.0 means perfect agreement, 0 means no better than chance):

Three things from doing this surprised me.

1. The judge caught a mistake in my labels

Both judges disagreed with one of my hand labels. I looked again, and they were right: that case had the same pattern as another one I had marked the opposite way. I had made a slip. Calibration doesn't only test the judge, it tests your labels too.

2. The same judge gave different answers to the same input

I ran calibration twice with nothing changed. gpt-4o-mini gave a different verdict on one case the second time. Sonnet gave the same answers both times. A judge that can flip on identical input adds noise to every score it produces, and one run won't show you that.

3. My test bank was too easy

On the 16 hand-labelled cases, both judges scored a perfect 1.00. But in real runs, the cheaper judge made the mistakes I described above and the stronger one didn't. My test cases didn't separate the two judges. The real runs did. The next step is to add harder test cases built from the judge's real mistakes, like the "rejected" one.

What I changed

  • Switched the judge to the stronger model, because it agreed with the labels and gave stable answers.
  • Re-judged old runs without rerunning the agent. I save every run, so I could score the old summaries with the new judge. The two false failures passed. (A first attempt failed another case, because saved runs have the issue text removed for privacy. The re-judge now puts the text back from the local cache first.)
  • Kept the judge's job narrow. Simple rules already catch obvious lies, like claiming an action that never ran. The judge only handles what rules can't, like a wrong issue number or a rejection that's quietly left out.

What I'd tell someone adding an LLM judge

  • Give it one narrow question, not "is this good?"
  • Label some cases by hand and measure agreement before you trust its numbers.
  • Open every failure by hand at first. Some will be the judge's fault.
  • Run it twice on the same input. If the answers change, that's noise in your metric.
  • Build test cases from real mistakes, not only the ones you can imagine.

The code, test cases and run log are public: issue-triage-agent on GitHub. The judge is in evals/judge.py, the test bank in evals/probes.jsonl, and every run is written up in docs/experiments.md.
